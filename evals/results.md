# Eval results

Seven graded evals across three rounds, each run with the skill and as a no-skill baseline. Everything is
scored by `grade.py` comparing files (see [README.md](README.md)); the table is generated by
`collect_results.py` from the graded runs, not copied by hand.

|---|---|---|---|---|---|---|---|
| it. 1 | 1 stage the app | 10/10 | 106,977 | 30 | 10/10 | 75,338 | 15 |
| it. 1 | 2 cold revert | 9/9 | 83,275 | 15 | 9/9 | 71,188 | 9 |
| it. 1 | 3 cold replay for production | 11/11 | 69,651 | 9 | 11/11 | 66,716 | 10 |
| it. 2 | 4 dev box setup | 11/11 | 81,314 | 13 | 11/11 | n/a | n/a |
| it. 2 | 5 cold revert with drift | 9/9 | 78,146 | 13 | 9/9 | 69,538 | 8 |
| it. 3 | 6 dev box setup, no nudge | 11/11 | 74,751 | 12 | 11/11 | 50,927 | 8 |
| it. 3 | 7 cold revert, no nudge | 9/9 | 79,006 | 12 | **7/9** | 83,607 | 10 |

Rounds 1 and 2 used prompts that **ask** for rollback and repeatability ("I may want to roll this back, and I'll
want to do it again"). Round 3 drops that sentence and offers the skill only as an available option, with its
real description, to test whether it triggers unprompted. Eval 4's baseline token count is n/a because the run
was interrupted by an API usage limit and resumed; the harness reported no usage for it, so it is missing, not
zero. Wall-clock times for the cold runs in round 3 are not reported: they were inflated by rate limiting.

## What the numbers support

1. **When the user asks for rollback support, a strong agent without the skill does fine.** In rounds 1 and 2
   the baseline wrote its own scripts (`prepare-env.sh` / `rollback-env.sh`, `acme-setup.sh` with a manifest, a
   marked block in `.zshrc`, checksum-based drift checks) and a cold agent used them to revert correctly, even
   with a human's later edits in the files. It matched the skill on correctness every time, using roughly 10-20%
   fewer tokens. These evals do **not** show a correctness win in that setting.
2. **When the user doesn't ask, the skill is what leaves a record.** In round 3 the skill-available agent chose
   the skill from its description alone ("a multi-step config change with one irreversible step, and you might
   want to undo or repeat it") and left a ledger. The baseline did the job, left nothing, and a cold agent
   could then restore **7 of 9** things. It could not know the original git email or which lines were the
   earlier session's, so it declined to guess, left `.gitconfig` and `PROJECT_ENV=dev` alone, and said so. That
   was the right behaviour given what it had. The skill's cold agent restored 9 of 9 by running the recorded
   undo with `--merge`, which removed the setup's lines and kept the human's two additions.
3. **The cost is real.** Recording costs more at work time: +42% tokens on eval 1 and +47% on eval 6 versus the
   baseline, and 1.25x-2.8x the wall-clock where it was measured. Cold agents cost about the same either way
   (79k vs 84k tokens in eval 7, 78k vs 70k in eval 5).
4. **The artifacts differ even when correctness doesn't.** The baseline left a bespoke script plus edits to the
   project's README and `.gitignore` (and carried them into the production copy); each cold agent had to read
   and trust code it hadn't seen, and one flagged that the script had been modified after the setup. The skill
   leaves one standard, self-describing `.back-in-time/` folder. That is a maintainability argument, not a
   measured outcome.

## What came out of the evals (changes to the skill)

- The with-skill agent in round 1 hit a **false drift** (two steps touching one file), reported it, and worked
  around it. It was a real bug in the tool; it is fixed and covered by a test.
- A cold agent **deleted `.back-in-time/`** after reverting, which destroys the ability to replay. The docs, the
  generated `TIMELINE.md`, and the ledger's `README.md` now say to keep it.
- A cold agent **declined to run the bundled `fork` script** and replayed by hand instead. That is a reasonable
  caution about executing code from a ledger you didn't write, and the docs now say so explicitly.
- The drift scenario motivated **`undo --merge`**: remove only what a step added or changed and keep later edits.
- Alongside the evals, two adversarial reviews of the tool (about 35 agents) found and drove fixes for ~17
  further defects (stale snapshot reuse, silent under-restore, secret handling, a printed-command bug); each has
  a regression test.

## Limits of this evidence

- **n = 1 per cell**, one model family, and fixtures written for the occasion. This is a smoke test with sharp
  graders, not a statistically powered comparison; small differences are noise.
- **The skill changed between rounds.** Round 1 ran the pre-review v0.1.0; rounds 2 and 3 ran the v0.2.0
  candidate (commit `d6b1c85`). The with-skill cold agents in rounds 2-3 used features that did not exist in
  round 1 (`--merge`).
- **The graders are scenario-specific.** They check what these tasks require. The one text check (does the cold
  agent's report admit the sent notice couldn't be undone?) is a keyword test.
- **Triggering was one observation:** the description made the agent choose the skill once. The 20 queries in
  `trigger-queries.json` have not been run through an optimiser.
- Not tested: tasks where the agent has to undo effects with no file footprint (API calls, cloud resources),
  very large trees, or concurrent agents on one ledger beyond the unit tests.
